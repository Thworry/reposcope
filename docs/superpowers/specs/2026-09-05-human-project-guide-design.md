# Human project guide

RepoScope serves people deciding whether and how to use an unfamiliar public repository. The reader should learn concrete capabilities, the intended workflow, operating requirements, and tradeoffs without inspecting individual functions.

## Chosen direction

Preserve the existing editorial paper palette and bilingual interface. Replace count-led takeaways with source-backed examples and explanations of their practical significance. Four reading entries lead to capabilities, workflow/onboarding, architecture, and adoption constraints. Keep project-authored wording distinct from RepoScope's interpretation. Source links remain attached and pinned to the inspected commit. Raw repository content stays inert text.

The alternatives were a cosmetic-only refresh or requiring the optional model service for every reader. Neither addresses the existing local report's lost information. Improve the default report and the optional expert narrative together.

## Deliverables

1. Read familiar English and Chinese README headings for installation, desktop use, tutorials, feature previews, operating requirements, and limitations. Retain ordinary prose under onboarding headings and useful structured tables within existing bounds and source contracts.
2. Replace generic counts in reader takeaways with actual capability descriptions, documented steps, architectural explanations, and stated constraints. Add meaningful chapter links and explain how to use each piece of information. Tie commentary to its triggering source text; missing evidence stays explicit.
3. Give the optional expert panel a reader-oriented editorial contract: explain a project's concrete tasks, inputs, process, outputs, prerequisites, and limitations. Architecture should explain broad component responsibilities. Version the prompt to prevent old narratives from being reused.
4. Synchronize bilingual public documentation and relevant evaluation expectations; verify desktop, intermediate, and mobile layouts plus the existing quality gates.

## Boundaries

No new model provider, login permission, telemetry, paid service, or executable repository content. Keep existing report schema, score rules, bounded evidence limits, and cache validation. Existing GitHub social metrics remain factual context. No fabricated translation or unsupported product promises. Broader documentation discovery and richer downloadable-resource models are recorded as future cross-schema work rather than silently misattributed to README.

## Acceptance

A populated takeaway names a real project capability, step, component description, or prerequisite, with its source and a useful next reading target. Typical README onboarding paragraphs previously omitted are retained. Sparse documents stay honest. Repository strings cannot be mistaken for app instructions. Updated expert prompts require concrete explanations and remain within existing validated envelopes. Meaningful behavior tests, lint, formatting, type checking, build, browser tests, bundle and performance gates pass.
